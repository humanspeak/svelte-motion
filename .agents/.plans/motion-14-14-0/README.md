# Motion 14.14.0 parity

Generated by the improve skill on 2026-11-14 against `feat/motion-14.14.0` at `4665b907`. That is `origin/main` ("Bump version to v2.12.0"). At that commit:
- `motion` and `motion-dom` are pinned to 14.12.0, and the installed `node_modules` match;
- `package.json` says `2.12.0`.

The upstream range reviewed is `~/Github/motion` `v14.12.0..v14.14.0`: 48 commits across 14.13.0 (2026-11-12) and 14.14.0 (2026-11-13), 33 files, 17 of them under `packages/`. Almost all of it is one feature (layout velocity, PR #4047). The audit was a targeted upstream-delta survey, not a general codebase audit: every changed file under `packages/` was read, along with the seven new `dev/react` fixtures, and each change was checked against the svelte-motion code that would consume it. Nothing outside that delta was audited.

The survey was grounded by running code, in a disposable worktree, with nothing committed:
- **A scratch pin bump to 14.14.0**: `pnpm check` gave 0 errors; `pnpm test:only` passed 1710 of 1711, the one failure being the export tripwire (`getSpringOptions`).
- **A scratch page** porting upstream's seven layout-velocity fixtures, measured frame by frame in Chromium on a vite dev server (port 4391), on 14.12.0, on 14.14.0, and on 14.14.0 with the port from plan 003 applied. The numbers quoted in plans 003, 004 and 005 come from those runs. They were not repeated on a built package; each plan's first step re-measures.

Nobody was available to answer questions during the run, so the whole delta is planned and the decisions below are defaults.

## Maintainer decisions (defaults, to confirm)

- **Plan the whole delta.** Default taken.
- **Release as svelte-motion 2.14.0 using a `minor` label from 2.13.x.** Plan 001 sets `"version": "2.13.0"`; it is the only plan that touches `"version"`. The maintainer adds the label. No plan adds PR labels. **Flagged for confirmation**: if you would rather land 2.13.x, or skip the label, only plan 001 Step 3's version line changes.
- **Standing rule: wherever we diverge from upstream, adopt upstream behaviour.** This is why plans 004 and 005 exist. Both fix divergences older than this release that upstream's new tests exposed.

## What arrives with the pin bump (no port)

- **`mass: "auto"`**: the spring type widens to `number | "auto"`, the spring generator stops warning about it, and motion-dom's projection node resolves it from the element's size (`resolveAutoMass`). Our transition type is motion's own (`src/lib/types.ts:306`). Measured on 14.14.0 with no port: a 500 px box settles about 650 ms after a 50 px one. Plan 001 pins the generator change with a red-first unit test; plan 003 pins the layout effect with upstream's three browser tests.
- **Most of layout velocity**: per-edge springs, the nested child keeping its place, the zero-size guard, the delay showing the start. All of it lives in `create-projection-node.ts`, which we use unchanged through `HTMLProjectionNode` (`src/lib/utils/motionDomProjection.ts:512`). The exception is recording the velocity on the snapshot: see plan 003.
- **`pinch`: a drag that starts during the snap back no longer stops scale and rotate** (#4076). We re-export `pinch()` and the `pinch` prop calls motion-dom's `addPinchListeners`. Plan 001 adds a red-first browser test.
- **`IProjectionNode.currentAnimation` is now `AnimationPlaybackControls`** (was `JSAnimation<number>`), and `edgeValues` was added. The adapter only tests `currentAnimation` for truthiness; `pnpm check` is clean on 14.14.0.
- **`getSpringOptions`** becomes a runtime export. It is an internal; plan 001 allowlists it.

## Findings considered and rejected

- **Keeping motion-dom's own `willUpdate()` snapshot instead of porting the velocity block.** motion-dom's snapshot already has the velocity, and the adapter overwrites it. But the adapter overwrites it for recorded reasons (a live read can race the DOM patch; a node mid animation must snapshot its on-screen target), so plan 003 adds the velocity to the hand-built snapshots instead. Plan 005 revisits one of those reasons under a gate.
- **`VisualElement.claimTarget` and the `shaders` animation-target type**: added (`510e7b522`, `c11dd60aa`) and removed (`94a35e0b3`) inside the range. Nothing to port.
- **Re-exporting `getSpringOptions`, `resolveAutoMass` or `pointToProgressVelocity`**: the first is exported without a `@public` tag for Motion UI's use; the other two are not exported by motion-dom at all.
- **Porting `LazyMotion/__tests__/hydration.test.tsx`**: it tests React `Suspense` and `hydrateRoot`. Plan 001 adds a node-identity guard instead.
- **Porting `projection/animation/__tests__/layout-velocity.test.ts`**: it unit-tests two functions motion-dom does not export. Plan 003's browser tests cover `resolveAutoMass`'s effect. Velocity along a curved `arc()` layout path (`pointToProgressVelocity`) has no upstream browser test and none here.
- **The removed `MotionGlobalConfig.layoutVelocity` flag** (`f87266545`, removed by `0cc935ac8`): never released.
- **A velocity opt-out prop**: upstream has none.
- **`animateLayout()` (vanilla)**: `src/lib/utils/animateLayout.ts` was not traced for velocity. It builds its own update around motion-dom nodes; whether an interrupted `animateLayout` spring carries velocity is unknown. See "Not read".
- **Size-budget commits, `dev/` package bumps, `lerna.json`, `yarn.lock`**: no runtime surface for this library.
