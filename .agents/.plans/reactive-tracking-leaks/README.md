## Found while writing plans 006–016 (not planned)

- **Finding 13's "size and inset keys still tween" is probably wrong.** Reading motion-dom, the node already has `shouldReduceMotion`, so `width`/`height`/inset are already instant. Only the transform keys our filter strips are affected. 013's red tests are written against the observable behavior either way.
- **A third naive `;` split** is in `layout.ts:107-116` (`stripNonChildLayoutStyle`). It only builds a comparison key, so 008 leaves it alone; it's a one-line follow-up.
- **008 side effect with `!important`.** After 008, a user's own `!important` declaration stays next to the library's appended hold (for example `display:none`) and now beats it. 008's Maintenance notes cover this.
- **Upstream `viewport.once` divergence, kept on purpose.** By reading, upstream doesn't disconnect the observer on `once`, so `onViewportEnter` can fire again after the element leaves and returns. Ours disconnects, which matches what both projects document. Consider raising it upstream.
- **Docs demo bug.** `docs/src/lib/examples/use-reduced-motion-config/demos/Default.svelte` calls `useReducedMotionConfig()` outside its own `<MotionConfig>`, so its readout never follows the radio buttons.

## Direction suggestions

Options for the maintainer, not ranked against the bugs above. Effort is
coarse. The motion.dev links were not fetched during the audit.

1. **`transformViewBoxPoint` for SVG drag.** Upstream ships a small public
   helper (`packages/framer-motion/src/utils/transform-viewbox-point.ts`) that
   returns a `transformPagePoint` for a scaled `viewBox`. `MotionConfig
   transformPagePoint` is already supported here; the helper is absent from
   `src/lib` and from `motionExportAllowlist.ts`. WOW: drag a `motion.circle`
   inside an SVG with `viewBox="0 0 100 100"` rendered at 500 px and it stays
   under the pointer instead of moving five times too far. Live reference:
   <https://motion.dev/docs/react-drag>. Effort S–M, additive. Trade-off:
   demand is unproven.
2. **Close the React-entry hook gap.** The README's stated goal is that React
   examples translate "with minimal changes", but `useDragControls` (only
   `createDragControls` exists), `usePageInView`, `useInstantTransition`,
   `useAnimateMini` and vanilla `followValue` are neither exported nor
   allowlisted. The export tripwire in `src/lib/index.spec.ts` covers the
   `motion` barrel but not upstream's React entry. WOW: paste the motion.dev
   drag-controls example (press a handle elsewhere and a different element
   starts dragging) and the import line works unchanged. Live reference:
   <https://motion.dev/docs/react-use-drag-controls>. Effort M in total, each
   piece S. Trade-off: more aliases to maintain; extending the tripwire to the
   React entry is the durable part.
3. **Finish `LazyMotion` feature gating (open issue #515).** `domMin`,
   `domAnimation`, `domMax` and `pinchFeatures` are exported and pinch is
   already gated per nearest `LazyMotion`, but animations are not gated on the
   bundle's flag and the README never mentions `LazyMotion`. WOW: the
   bundle-size story, an `m` component whose first paint ships a few kilobytes
   and whose animations switch on when the feature chunk arrives. Live
   reference: <https://motion.dev/docs/react-lazy-motion>. Effort M, risk MED
   (changes behaviour for `m` without a bundle). Best started as a spike that
   defines the no-bundle behaviour and extends the tree-shaking guard to prove
   the size claim.

## Findings considered and rejected

So nobody re-audits them:

- **`LazyMotion` swallows loader rejections** (`LazyMotion.svelte:84-91`): the
  in-code comment records it as a deliberate choice ("publishes nothing, as
  upstream"). Upstream has no `.catch`, so it surfaces an unhandled rejection
  where this stays silent; logging the error in dev would be a small
  improvement, not worth a plan.
