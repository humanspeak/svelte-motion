## Findings considered and rejected

- **Port the direction-lock fix (`e35b1d610`)**: svelte-motion's `drag.ts` already applies the move that sets the
  lock (`drag.ts` around lines 1092-1134).
- **Port the `useSpring`/`useFollowValue` catch-up (`90caa485a`, `a3a375c3d`)**: `followValue.svelte.ts` reads the
  source and calls `attachFollow` in the same tick, and teardown destroys the value. There is no render→effect gap.
- **SVG MotionValue children (`a26b02623`)**: `children` never reaches `svgEffect` in svelte-motion
  (`_MotionContainer.svelte` destructures it; `motionValueChild.ts` renders it).
- **`<Activity>` sync (`3da0dd049`)**: React-only.
- **Patch the window-scroll, `var()`/`%` origin and drag-style gaps in svelte-motion's own drag**: the maintainer
  chose (2026-10-21) to spike adopting upstream's controller first (006); patching code that may be deleted is
  wasted work.
- **`restore()` overwriting a synchronously committed transform in `commitDraggedLayoutChange`**: real window but
  very unlikely; recorded as a watch item in 001 rather than planned.
- **Dead `buildTransform`/`isSafeTransform`/`parseMatrixScale` in `src/lib/utils/transform.svelte.ts:16-110`**
  (2D-only key list, no `scaleZ`; used only by specs): out of this initiative's upstream-parity scope. Worth a
  separate tech-debt cleanup.
