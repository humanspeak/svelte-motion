# Motion 14.9.1 parity

Generated by the improve skill on 2026-11-04 against `origin/main` `fb9ed218`. At that commit `motion` and `motion-dom` are pinned to 14.7.1 (merged as #511) and `package.json` says `2.5.1`. The upstream range reviewed is `~/Github/motion` `v14.7.1..v14.9.1`, which covers four releases (14.7.2, 14.8.0, 14.9.0, 14.9.1, released 2026-10-29 to 2026-11-04). The `motion/remix` adapter was skipped: it is a separate framework port that this library doesn't use.

The maintainer asked on 2026-11-04 to go straight to 14.9.1 in one batch and to **land on svelte-motion 2.9.1**. The publish workflow (`.github/workflows/npm-publish.yml`, "Determine version bump type") runs `pnpm version patch` on a merged PR that has no `minor`/`major` label. So plan 001 sets `"version": "2.9.0"` in `package.json`, and the release workflow publishes that as 2.9.1. That is the only plan that touches `"version"`. No plan adds PR labels. If `main` has moved to `2.5.2` by merge time (the #511 publish), keep `2.9.0` when resolving.

The maintainer's standing rule: wherever we diverge from upstream, adopt upstream behaviour.

## What arrives with the pin bump (no port)

These are motion-dom changes. Our code calls them and does not re-implement them, as checked against our code at `fb9ed218`:

- `transition.mixer` (14.8.0; bcf8a238e, 1a81c374f, ed27f9688, 563b275fa). Our `MotionTransition` is motion-dom's `AnimationOptions` (`src/lib/types.ts:299`). Plan 006 documents and demonstrates it.
- SVG path data is written to the `d` attribute and removed when unset (0757359b3, f84dcecf6). `svgEffect` is a passthrough (`src/lib/utils/effects.ts:173`).
- Timeline changes stay inside their `scopeMotion` scope (8fb99ce66). `scopeMotion`, `Timeline` and `createScopedAnimate` come from `motion` (`src/lib/utils/scopeMotion.svelte.ts:1`, `src/lib/utils/animateValue.ts:1-8,193`).
- `jump()` stops the animation first and skips the catch-up tick (91763bdf1, db88ba821, #4027). This fixes 14.8.0's "accelerated animations stuck at `initial` after remount". Our key-change rewind and `set()` paths go through `jump()` (`src/lib/html/_MotionContainer.svelte:3663,3780`). Plan 001 pins it.
- WAAPI finish handlers are released and reattached, and transforms that can't be accelerated still finish (7ba5aafae, bcfb14617, 8b3cf65cb). Also 14.9.1's "accelerated animations are cleaned up in WebKit".
- An exit is no longer stuck after an open `layoutId` card switches to another item (f77c399f4, #4042). The fix is in motion-dom's `notifyLayoutUpdate`. Our `switchLayoutId` (`src/lib/utils/motionDomProjection.ts:677-730`) reaches the failing state, so plan 001 adds the upstream repro page.
- Vanilla `drag()` measures without the projection system, and a released drag node is detached (75c81d7e7, a415c9ae0). Our `drag` is re-exported from `motion` (`src/lib/index.ts:30`).
- Projection stats are only counted while `recordStats()` runs (41aeb12b6). We don't export `recordStats` (`src/lib/__tests__/motionExportAllowlist.ts:368`).
- `keepValuesOnRemount` on `PresenceContext`, and values are kept when an element is shown again only to exit (6e5968f1f, 0a0584bef). Both read `isPresent`, which we already supply (`_MotionContainer.svelte:451-465`). Nothing in Svelte needs `keepValuesOnRemount`.

Not planned:
- `pathConstraints` was added and removed again inside the range (8a8e882c3 … a6a03eada). Only the `dragConstraints` function hook ships, and plan 005 covers that.
- Projection node setup moved to `ProjectionNode.create` (e219b1be7, 0342ce75c). This is a bundle-size refactor. We construct `HTMLProjectionNode` ourselves (`motionDomProjection.ts:512`), and its constructor is unchanged.
- `ValueSequence` became an interface (87b4ec30b). We don't re-type it.
- Size-budget commits.
